# Go review

This skill holds every personal Go rule. Read it fully before writing, modifying, or reviewing Go. When reviewing, check correctness and adherence to these rules and to the guideline files.

## Guidelines source of truth

Read both files located in the same folder as this SKILL.md before reviewing and treat them as the standard:

- `concurrency.md` (goroutine lifecycle, channels, close responsibility, bounded parallelism, data races, `sync`)
- `idioms.md` (declaration idioms, argument order, package layout, interfaces, errors, mutexes, tooling)

## Go rules

These rules apply when writing Go and are checked when reviewing it.

### Tests

- Prefer table-driven tests using a `map[string]struct{}` (not a slice) for test cases
- Use `testify` (`assert`/`require`) for assertions, never use testify's suite
- Use `t.Parallel()` whenever possible (both at the top-level test and subtests)
- Don't make external test package or black-box testing. Write the tests in the same package.
- Always run `go test -race` (include the `-race` flag)

### Mocks

- When mocking is needed, use `//go:generate` directives and generated mocks. Never write mocks or stubs manually

### Errors

- Wrap with `fmt.Errorf("doing something: %w", err)`, never prefix with "error", "failed to", "error while". Just state the action (e.g. `"opening file: %w"` not `"failed to open file: %w"`). The same applies to panic and log messages.

### Readability

- Add blank lines to separate logical groups of statements (e.g. after variable declarations, before return statements, between distinct steps of a function, around loops and conditionals). Never write dense walls of code. Vertical whitespace is mandatory for human readability.
- Variables must have at least 3 characters; exceptions: `a`, `b` when identity is irrelevant (e.g. swap), `i`, `j`, `k` for index-based loops, and single-letter names established by language convention (e.g. `t` for `*testing.T`, `r`/`w` for the request/response of an HTTP handler). Other parameters need at least 3 characters.
- Receivers are the exception to the 3 characters rule: letters made of the first letter of each word of the type name in camelCase/PascalCase (e.g. `Pool` is `p`, `forwardSet` is `fs`, `Logger` is `l`). Never flag a short receiver, flag one that does not follow the initials of its type.

### Comments

- Only add a comment when the WHY of the current code is non-obvious
- Doc comments are present only when the code has an unusual behavior or an unconventional design that a reader could not infer from the code and its name. Never flag a missing doc comment on an exported symbol, and never add one that restates the name or signature.
- Never write a package level doc comment (`// Package foo ...` above `package foo`)
- Comments describe current behavior only. No "before/after", "previously", "used to", "now we", "instead of", "removed X" style comments or comparisons with a previous version.
- When reviewing, flag comments that restate a name or signature, that describe history, or that sit on code whose behavior is obvious

### Modern Go

- Write code for the Go version in `go.mod`, not for the Go of the training data. Use the current idioms of that version: `slices`, `maps` and `cmp` instead of `sort`, integer `range`, `min`/`max` builtins, `wg.Go`, `strings.SplitSeq`/`FieldsSeq`, `errors.Join`, `any`, `new(expr)` when available, and so on. Never write the legacy form that `go fix` would rewrite (e.g. `sort.Strings`, `interface{}`, `for i := 0; i < n; i++` without needing `i` semantics, manual loop copies, `x := x` loop variable captures).
- When reviewing, flag legacy constructs that `go fix` would modernize.

### Tooling

- After changing any `.go` file, always run `go fix .` in its package directory (the editor flags every legacy construct it would rewrite), then `gofumpt -extra` on the file, unless the file starts with `// Code generated by` (skip both for generated files). Run `go fix` first, so the formatter sees the final code.
- Read the diff of what `go fix` changed in files you did not touch before keeping it, and mention unrelated rewrites to the user instead of silently mixing them with the task.
- After completing all changes, run `golangci-lint run --fix --show-stats=false --allow-parallel-runners .` in each affected Go package directory and check the output for errors

## Scope

Pick the scope in this order:

1. **Explicit target**: if the prompt or argument names a folder, review all non-generated `.go` files in that folder (recursively, including `_test.go`). If it names a file, package, or ref, review that instead.
2. **Working changes**: otherwise review the current working changes only. Determine the diff read-only:
   - `git diff <default_branch>...HEAD` for committed work on the branch (find the default branch with `git rev-parse --abbrev-ref origin/HEAD`, always compare against origin)
   - `git diff` and `git status` for uncommitted work
3. **Current folder fallback**: if there is no explicit target and the diff is empty (or git is unavailable), review all non-generated `.go` files in the current working directory, recursively. Say so in the output so the user knows no diff was found.

For folder reviews there is no diff to anchor on, so read each file in full. If the folder is large, review package by package and report per package.

Never run any mutable git command.

## What to check

The two guideline files are the only checklist. Do not rely on memory or on a fixed list of rules.

1. Read both files in full, section by section.
2. Treat every section as a rule set to verify against the code under review. Lines starting with `Idiomatic Go`, `Do`/`Don't` examples, bold statements (**always**, **never**, **should not**) and rules of thumb are normative.
3. For each section, decide whether the changed code touches its topic, and if so check it. Skip sections that do not apply.
4. Cite the section heading of the file for each finding, so findings stay traceable when the files change.

Review rules that are not in the guideline files:

- The guidelines assume a recent Go toolchain. Check the Go version in `go.mod` before suggesting version-gated features (`wg.Go`, integer `range`, `b.Loop`).
- Where the guideline files and the Go rules above overlap, the Go rules above win.

## Output

Group findings by severity (blocking, should fix, nit). For each: `file:line`, the issue, and the concrete fix. Cite the relevant guideline section. Be concise, and follow the communication style in `~/.config/AGENTS.md` (no dashes or hyphens as punctuation). Skip generated files (`// Code generated by`). Do not edit files unless explicitly asked.
